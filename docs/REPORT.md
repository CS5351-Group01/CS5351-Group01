## 1. 背景与目标

### 1.1 问题

现有 AI 改代码工具大多是一次性给建议：

```text
贴代码 → 模型给一段修改 → 用户自己判断对不对 → 自己贴回去试
```

**关键缺口是没人验证。** 模型说"修好了"，是不是真修好了，用户得自己跑一遍。

### 1.2 我们做的

把「生成」和「验证」闭成环：

```text
有 bug 的代码
    ↓
大模型生成修复
    ↓
在隔离沙箱里应用
    ↓
真的跑测试
    ├── 通过 → 交付
    └── 不通过 → 失败信息回灌，再来一轮
```

### 1.3 交付形态

网页应用：浏览器上传 `.py`，看着它被自动修复，最后看到「修复前 / 修复后」逐行对比。

## 2. 系统架构

### 2.1 分层

```text
frontend/     浏览器页面：上传、轮询进度、前后对比、历史列表
     ↓ HTTP
app/          FastAPI：注册登录、JWT 鉴权、文件存储、任务调度
     ↓ 后台任务
llm/          闭环修复：拼 prompt、调模型、解析回复、多轮重试
     ↓ 调用
sandbox/      隔离执行：复制到临时目录、跑 pytest、超时与输出限制
     ↓ 依赖
agent/        工具层：技能（ls/read/grep/write/find）、记忆、补丁落盘
```

### 2.2 四层边界

| 层 | 只做什么 | 不做什么 |
|---|---|---|
| `frontend` | 发请求、渲染结果 | 不做业务判断 |
| `app` | 鉴权、存储、派任务 | 不碰模型，不碰沙箱 |
| `llm` | 问什么、怎么解析、要不要重试 | 不直接读写文件、不跑进程 |
| `sandbox` | 复制、跑、清理 | 不知道什么叫"修复" |
| `agent` | 对工作区做原子操作 | 不知道什么叫"一轮" |

为什么这样分：每层只有一个变化理由，出问题能定位到层；六个人各占一个目录，才能并行改而不互相踩。

反面例子：如果 `SandboxWorkspace` 直接在原目录上改，模型写出一份半截文件（比如 `return a -`）后 pytest 超时，
原文件已经被覆盖，下一轮只能拿这份坏代码继续修，用户上传的原始版本也没了。
`tests/roles/c/test_sandbox_isolation.py::test_source_file_untouched_including_mtime`
就是锁这条的：在沙箱里改 `calc.py`，原文件的内容和 mtime 都不许变。

### 2.3 关键设计决定

| 决定 | 理由 |
|---|---|
| 模型返回**整份文件**，不是 diff | 写对 diff 应用器比写对整文件替换难得多，而修复本来就是「给错代码，还对代码」 |
| 沙箱永远在**副本**上跑 | 原目录一个字节都不动，测试里专门验了这条 |
| LLM 客户端可替换（`FakeLLM` / `OpenAICompatClient`） | 没 key 也能跑通全流程；CI 不依赖网络和钱 |
| 实验强制自报客户端身份 | 见 6.4，静默降级差点让假数据冒充真数据 |

## 4. 闭环修复怎么实现的

### 4.1 一轮里发生了什么

```text
1. build_fix_prompt(代码, 上一轮失败输出, 第几轮)
2. client.complete(prompt)          → 模型返回带 ```python 的回复
3. extract_code_block(回复)         → 抠不到代码就算这轮失败
4. workspace.write(target, 候选)     → 落到沙箱副本
5. run_pytest(沙箱根目录)            → 真的跑测试
6. 通过 → 交付；不通过 → 截断输出作为下一轮反馈，回到 1
```

### 4.2 为什么设 `max_iters`

模型一直改不对时，循环必须有硬上限：`app/services/task_runner.py` 里 `MAX_REPAIR_ITERS = 3`，
`llm/iterative_fix.py` 的 `repair_source(max_iters=3)` 到第 3 轮直接返回
`RepairOutcome(success=False, message="3 轮内未能修复")`，任务落 `failed`，每轮失败摘要留在 `report` 里。

为什么是 3：每轮 = 1 次模型调用 + 1 次 pytest（真模型实测单轮 1.5~3 秒，见 6.2），
3 轮上限约 5~10 秒，用户还能等；再往上加，失败信息大多重复，收益递减。
`max_iters` 是参数，测试和实验可以覆盖（比如进度测试用 2 轮），默认值只服务线上任务。

### 4.3 沙箱的三道保护

| 保护 | 实现 | 位置 |
|---|---|---|
| 不在原目录改代码 | 复制到临时目录，退出时删除 | `sandbox/workspace.py` |
| 单次执行超时 | `subprocess.run(timeout=...)` | `sandbox/runner.py` |
| 输出长度上限 | `truncate_output()`，超了打标记 | `sandbox/limits.py` |

三道保护都不是预先设计的，各自对应一次真实故障。补测试的过程中还暴露出两处泄漏。

**第一道：目录隔离 —— 对应「失败的补丁把用户项目改坏」。**
模型生成的补丁可能语法错、可能改错文件，一旦直接落在用户目录就无法回滚。
实现把项目复制到临时副本，`with` 退出时删除。补这道保护时抓到两处泄漏：

- **进入失败时临时目录残留。** `__enter__` 先 `mkdtemp` 再复制，复制阶段抛 `SandboxError` 时
  `__exit__` 不会被调用，目录永久留在临时区。测试中拦截 `mkdtemp` 取得路径，再断言它已不存在。
- **异常穿透到调用方。** 向不存在的 cwd 启动 pytest 会抛 `NotADirectoryError`，原实现只捕获
  `TimeoutExpired`，于是「上传目录中途被删」会让整个任务返回 500，而不是按单轮失败处理。

**第二道：时间 —— 对应「一段死循环拖死服务」。**
最初只有单次 60 秒超时，能挡住单轮，挡不住多轮累加：3 轮各卡一次就是 180 秒。
后来补 `TimeBudget`：给整个任务一个预算（默认 120 秒），每次调用取 `min(单次超时, 剩余预算)`；
预算见底后不再启动子进程，直接返回失败并写明「总时间预算 Ns 已用完，任务中止」。
即使调用方忽略返回值继续循环，也不会再产生新进程。

**第三道：输出上限 —— 对应「一次失败输出撑爆内存和 prompt」。**
打印十万行的测试会同时撑大进程内存与模型上下文。原实现按 `[-8000:]` 静默截断，
调用方无法判断内容是否完整；现在保尾部（结论行在最后）、开头插 `…[输出已截断]…`，
并把 `RunResult.truncated` 暴露给上层，模型从反馈里也能看出「这里不完整」。

三道保护各有一条可复现的测试，见 `tests/roles/c/test_sandbox_isolation.py`。

## 6. 真模型实验

### 6.1 设置

```text
模型：deepseek-chat
接口：https://api.deepseek.com/v1
用例：examples/ 下共 7 个（5 个基础语法错 + 2 个高难度逻辑陷阱）
```

### 6.2 结果

| 用例 | 结果 | 轮数 | 耗时(s) |
|---|---|---|---|
| broken_project | PASS | 1 | 2.94 |
| empty_input | PASS | 1 | 1.75 |
| name_error | PASS | 1 | 1.55 |
| off_by_one | PASS | 1 | 2.03 |
| syntax_error | PASS | 1 | 1.93 |
| **hard_plural** (高难) | **PASS** | **2** | 2.19 |
| **hard_dedup** (高难) | **PASS** | **2** | 2.77 |

通过率 **7/7**，平均 **1.29 轮**。

### 6.3 这个数字说明什么、不说明什么

**说明**：从上传到沙箱验证到结果回传，整条管路是通的，真模型接上就能用。并且，**闭环迭代机制在难例上发挥了真实作用**，平均轮数从最初的 1.0 上升到了 1.29，这正是系统在“挣扎并重试”的体现。

**不说明**：模型能一次就做对。前 5 个用例都是很浅的错（缺冒号、名字拼错、少个加号），一次做对不奇怪。**真正的实验数据来自于新加的 2 个难例**：

*   **区分度测试**：假模型（仅靠预置修复表）在这 7 个用例上只能通过 5/7，说明新难例成功避开了“背答案”。
*   **闭环能力验证**：真模型在 `hard_plural` 和 `hard_dedup` 上，**第一轮均生成失败**（报错或被拦截），系统将 pytest 错误回灌后，**第二轮成功修复**。这才是本项目“闭环迭代”核心卖点的最佳证明。

### 6.4 一个差点酿成事故的坑

第一版真模型报告显示 5/5、每个 1.1~2.0 秒。但**假模型也是这个耗时**。

排查发现：`default_client()` 在没有 `LLM_API_KEY` 时**静默退化**成 `FakeLLM`，跑出来照样 100%，报告上完全看不出来。

修法：降级时往 stderr 吼一句，并让实验输出第一行强制自报身份：

```text
客户端：OpenAICompatClient (model=deepseek-chat)
```

**教训与工程原则**：**任何降级都不能静默（No Silent Fallback）**。静默降级会让假数据穿上真数据的外衣，蒙蔽开发者。这体现了系统设计中的 **Fail-Fast（快速失败）** 原则——如果缺少 Key，系统应当大声报错或明确输出警告，而不是自作聪明地用假数据伪造成功。

## 7. 局限与后续

| 局限 | 现状 | 后续怎么做 |
|---|---|---|
| 用例梯度不够长 | 7 个用例里 5 个是单点小错，只有 2 个难例 | 补跨函数调用、多文件依赖、需要重构的用例，形成 3~4 档难度 |
| 只支持单文件 | 上传一个 `.py`，测试要和它放一起才能验证 | 支持 zip 项目，自动发现测试 |
| 没有并发控制 | 多任务同时跑会抢 CPU 和临时目录 | 加任务队列和并发上限 |
| 前端没有自动化测试 | 只有手工验证和截图 | 引入 Playwright 做端到端 |
| 依赖模型输出格式 | 格式不对（没有代码块）就浪费一轮 | 重试 + 更强的输出约束 |
| 只支持 Python | 检查器写死了 `py_compile` / `pytest` | 按语言抽象 test runner |

## 答辩可能被问的问题

1. **修复率 100%，说明模型很强吗？**
   → 不是。用例太浅，见 6.3。

2. **模型一直改不对怎么办？**
   → `max_iters` 兜底，超了报失败，每轮记录留在报告里。

3. **用户传的代码会不会搞坏服务器？**
   → 副本隔离、超时、输出上限、`.py` 白名单。**但没做容器级隔离**，这是已知局限。

4. **六个人怎么协作，会不会互相改代码？**
   → CI 强制路径所有权，两道锁。举一个被拦的真实例子。

5. **为什么用假模型测试，有意义吗？**
   → 假模型是为了让流程可测、CI 不依赖网络和钱。真模型能力另外测，两者分开。

6. **最有技术含量的部分是什么？**
   → 沙箱的资源控制 + 闭环的失败回灌。

7. **再给两周会做什么？**
   → 见第 7 节。
